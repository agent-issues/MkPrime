| T-006 | P0 | **APPLIED (2026-05-19), VERIFIED 26.6 % on top of T-005 (30.5 % vs baseline)** | [Optimise] | Tip-edge fast path in `persite_impl` exploits one-hot child CL | `src/mcmc_likelihood.cpp` (`persite_impl` template — `tipChild` branch before the internal-child propagation). **Insight:** when `ch <= nTip`, the child CL for each character is one-hot for the observed state (`clCh[s]=1`, rest 0) or uniform-1 for missing data. `sum_cl` is therefore 1 (known) or K (missing) by construction — no need to load and sum the K clCh entries. The per-state update collapses: known → K writes of `p_diff` + 1 overwrite of `p_same`; missing init → K writes of 1.0 (the JC marginalisation identity `K·p_diff + (p_same − p_diff) = 1`); missing multiply → no-op (×1). **Verified by micro-bench** (5 runs each, Sun2018 EG production-weight workload, 800 iter): T-005-only median **16.45 s** → T-005+T-006 median **12.07 s** (mean 12.07, sd 0.084). **Δ = 26.6 % on top of T-005, 30.5 % vs baseline** (baseline median 17.39 s). Welch t-test t = 35.4 on 5.7 df, p < 10⁻⁶. **VTune confirms** `persite_impl<0>` (runtime K > 24) 6.802 → 4.413 s; sum of all persite specialisations ~7-8 s vs baseline 15.088 s — **~50 % reduction in CL pruning self-CPU**. **Why so much:** ~50 % of edges in a 54-tip tree are tip-incident; for each, K loads of clCh + K-1 sum_cl adds + K multiplies eliminated per character per rate category. The savings compound multiplicatively with K, so the Gibbs k′ sweep (K up to 50) sees the biggest absolute gain. **Tests:** 234/234 across `filter="likelihood|gibbs|ascertain|mcmc-engine"`. Mathematical identity verified analytically (above) and empirically (zero test failures including Gibbs k′ posterior comparisons). **Maintenance cost:** ~50 LoC; one mathematical insight; no duplicate code path (T-005 refactor ensured single shared body across compile-time-K and runtime-K). |
| T-005 | P0 | **APPLIED + REFACTORED (2026-05-19), VERIFIED 5.4 %** | [Optimise] | Compile-time-K dispatch on `pruning_jc_acrv_persite` (single-body template) | `src/mcmc_likelihood.cpp` (new `persite_kfixed<K>` template + `persite_generic` fallback, switch-dispatch in `pruning_jc_acrv_persite`). Reasoning: the original function had `kStates` as a runtime parameter, forcing the inner per-state loops (`for j<kStates`, `for i<kStates`) to be runtime-bounded. K is small (2–24 in practice; K_MAX_CAND=50 is the absolute cap from `src/mcmc.cpp:3322`), so a switch on K dispatching to a compile-time-K template lets the compiler fully unroll the inner loops and emit straight-line per-state FMAs. Specialised K = 2..24; K > 24 falls into `persite_generic` (bit-identical to the pre-T-005 code). Inner loops carry `#pragma GCC unroll 8` hints; pointers marked `__restrict__`. **Verified by micro-bench** (driver `dev/profiling/drivers/01_bench_t003.R`, Sun2018 54×225 EG production-weight workload, 800 iter, 5 runs each): baseline median **17.39 s** (mean 17.47, sd 0.28); T-005 median **16.75 s** (mean 16.70, sd 0.20). **Δ = 4.4 % wall-time speedup, p < 0.01 (Welch t-test, t=4.3 on 7.4 df).** Tighter variance under T-005 too. **VTune verification:** `persite_generic` self-time **15.088 s → 7.113 s** in MkPrime.dll (Sun2018 EG hotspot collection, software sampling); difference absorbed by `persite_kfixed<2..24>` (combined ~4.5 s of self CPU, dominant in K∈{19..24}). Tests pass (53 / 53 across `filter="likelihood|gibbs-kprime"`, including the `test-gibbs.R` suite that exercises Gibbs k′ sweep). **Why only 4.4 %, not the predicted T-003 75 %:** the remaining `persite_generic` 7.113 s is K > 24 candidate-k values that the EG prior's heavy tail still puts non-trivial weight on. Extending the specialisation higher is straightforward (add `DISPATCH_K(25)` … in `src/mcmc_likelihood.cpp:pruning_jc_acrv_persite`) at the cost of binary bloat (~100 LoC of generated code per added K). Diminishing returns expected since per-K hotspot share decreases beyond K=24. **Further wins available** (deferred): (a) algorithmic — reduce candidate-k count via tighter early-termination criteria in `gibbs_kprime_sweep_impl`; (b) algorithmic — partial-CL across consecutive candidate-k values within one sweep step (major refactor); (c) explicit AVX2 vectorisation of the inner K loop for high K. The 4.4 % gain confirms the templating approach is correct but the next big jump needs algorithmic work, not codegen. |
