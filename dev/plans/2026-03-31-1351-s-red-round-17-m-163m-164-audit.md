## Audit Items

### M-163: BG Slice Sampler

#### A1. Target distribution correctness
Verify the log-scale slice sampler target is `logPrior(x) + log(x)` where `x = exp(u)`. The Jacobian `|dx/du| = exp(u) = x` gives `log|dx/du| = u = log(x)`. Confirm the initial threshold `logY0 = state->logPrior + u0` and subsequent `evalTarget` returns `lp + u` match this.

**Assessment:** Correct. The target on the u-scale is `logPrior(x(u)) + log(x(u))` which equals the `lp + u` in evalTarget.

#### A2. evalTarget restore logic
The lambda temporarily mutates `state->kprimeAlpha/Beta`, calls `cpp_log_prior()`, then restores the old value. Verify:
- (a) The old value is captured before mutation
- (b) `cpp_log_prior` reads from the passed state members (not from independent storage)
- (c) Restore happens unconditionally (not skipped on non-finite results)

**Assessment:** Correct on all three points. Lines 2928–2938.

#### A3. Cache invalidation
`slice_kprime_hyper_impl` does NOT set `state->nodeCL.valid = false`. Since kprimeAlpha/Beta only affect the prior (not the likelihood), node CLs are unaffected. Compare with `slice_scalar_impl` which does invalidate (line 2890) because its parameters (rateLogSd, etc.) affect transition probabilities.

**Assessment:** Correct — no CL invalidation needed.

#### A4. logPrior / logLik / logPosterior consistency
On acceptance (line 2964–2972): sets new alpha/beta, recomputes and caches `state->logPrior`. Does NOT touch `state->logLik` (correct, since alpha/beta don't affect likelihood). `logPosterior` is not cached — computed on-the-fly as `logLik + logPrior` at sample-recording time (lines 452, 4579). No staleness issue.

#### A5. Heated chain handling
The slice sampler's target is `logPrior + Jacobian` with no beta (tempering) parameter. This is correct: for heated chains, the posterior is `beta * logLik + logPrior`. Since alpha/beta are conditionally independent of the likelihood given kPrime, the conditional distribution for alpha/beta is just the prior, regardless of chain temperature.

#### A6. R wiring verification

- `.BuildMoves()`: Creates moves with `type = "slice_kprime_hyper"`, `sliceParamIdx = 0L/1L`. ✓
- `alwaysAcceptTypes`: Includes `"slice_kprime_hyper"`. Matches via `moveTypes %in% alwaysAcceptTypes`. ✓
- `.AdaptSliceWidths`: `sliceKeys` includes `slice_kprime_alpha → slice_width_kprime_alpha` and similar for beta. ✓
- `.AdaptTuning`: `tuningKeys` does NOT include entries for slice moves — but `is.na(tk)` guard at line 3575 correctly skips them. The `targets` vector (line 3534) has `slice_kprime_alpha = NA_real_`, ensuring no error on lookup. ✓
- `MkPrimeMCMC`: Defaults for `slice_width_kprime_alpha` and `slice_width_kprime_beta` both 1.0. ✓

#### A7. Dispatch in batch runner

#### A8. Edge cases

- **x0 <= 0:** Returns false immediately (line 2915). Defensive but shouldn't occur in normal operation.

### M-164: Gibbs kPrime Pre-filter

#### B1. LOG_CUTOFF tightening
Changed from -57.5 to -25.0. `exp(-25) ≈ 1.4e-11` relative probability. With 50 candidates at this threshold, total tail mass ≈ 7e-10, well below double-precision RNG resolution (~2.2e-16). Safe.

#### B2. Pre-filter correctness
The pre-filter at ko ≥ 2 computes `optimisticW = beta * charMaxLL[ti] + logPrior_k` and prunes if `optimisticW < charMaxLogW[ti] + LOG_CUTOFF`.

**Key assumption:** "likelihood tends to decrease with higher k". This is a heuristic. `charMaxLL[ti]` is the maximum corrected log-likelihood observed so far (ko = 0..ko-1). If the true LL at ko genuinely exceeds charMaxLL, the pre-filter could incorrectly prune.

**Risk assessment:** In practice, this is extremely unlikely because:
- BG prior is monotone-decreasing in ko, so the combined weight decreases even if LL increases
- The 25-log-unit slack gives enormous margin
- For chars with kObs ≥ 2 (the only ones affected, since filter runs at ko ≥ 2 and these have kObs ≥ 2), the LL at ko = 0 (k = kObs) is typically near-optimal

**Action:** Note as theoretical concern in S-RED log, not a practical bug. Could add a debug-mode assertion to verify the invariant is never violated on test datasets.

#### B3. charMaxLL tracking
Initialized to `R_NegInf` (line 3314). Updated at line 3455: `if (R_FINITE(ll) && ll > charMaxLL[ti]) charMaxLL[ti] = ll`. The `R_FINITE` guard prevents non-finite LLs from polluting the tracker. ✓

#### B4. nActive consistency
`nActive` starts at `nTrans` (line 3319). Decremented at two sites:
- Pre-filter (line 3381): when `terminated[ti]` is set
- Post-evaluation (line 3474): when character terminates after LL computation

Both sites also update the per-partition active arrays. Each character belongs to exactly one partition. No double-decrement possible since `terminated[ti]` prevents re-processing. ✓

Wait — **potential double-decrement bug**: At the pre-filter (line 3378–3381), the code checks `optimisticW < charMaxLogW[ti] + LOG_CUTOFF` and sets `terminated[ti] = true; nActive--`. But what if `terminated[ti]` was already true? In that case, the character wouldn't be in the active set (since prior ko iterations filtered it out via the post-evaluation termination at lines 3472–3478 which removes it from `pa.activeCols`). So the guard is implicit via the active-set filtering. ✓

#### B5. R_NegInf edge case
If both ko = 0 and ko = 1 give R_NegInf for a character, it would be terminated by the post-evaluation check (`!R_FINITE(ll)`, line 3472) at ko = 0, and never reach the pre-filter. If only ko = 0 gives R_NegInf, `charMaxLL` would be updated at ko = 1, so by ko = 2 it's finite. ✓

#### B6. Heated chains
`charMaxLogW` stores `beta * ll + logPrior_k`, and `optimisticW` uses the same `beta`. Comparison is consistent. For hot chains (beta < 1), the pre-filter is actually more conservative (less pruning), which is safe. ✓

#### B7. Vector allocation
`surviveCols` and `surviveTransIdx` allocated per-ko per-partition inside the pre-filter. Acceptable cost: vectors are small (bounded by nTrans), and only created for ko ≥ 2 when there are active characters. Moved via `std::move`. ✓
