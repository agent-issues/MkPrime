# M-159: Cache-aware move scheduling

## Problem

When the node CL cache is valid, partial-CL moves (NNI, beta_simplex,
Dirichlet, local_dirichlet) run ~15× faster than full-evaluation moves.
Currently, move selection in `run_mcmc_batch_cpp` uses fixed weights
regardless of cache state. This wastes wall-time: when the cache is valid,
we should preferentially select fast partial-CL moves.

## Design

### Statistical validity

State-dependent mixture kernels preserve the target distribution as long as
each component kernel individually satisfies detailed balance. Cache validity
is a deterministic function of the MCMC state (set by the previous move's
accept/reject outcome), so there's no additional randomness to account for
in the acceptance ratio. Each move's acceptance ratio is unchanged — only the
probability of *selecting* it changes.

### Implementation

**Two precomputed cumulative-weight arrays** in `run_mcmc_batch_cpp`:

1. `cumWeights_base[nMoves]` — current weights (used when cache is invalid)
2. `cumWeights_cached[nMoves]` — boosted weights for partial-CL moves (used
   when `state->nodeCL.valid == true`)

The boost is a multiplicative factor `cacheBonus` (default 5.0) applied to
moves with types {4, 5, 23, 24} (beta_simplex, NNI, dirichlet,
local_dirichlet).

Per chain per iteration, select which array to use:

```cpp
bool useBoost = states[ch]->nodeCL.valid && !data->qHeterogeneity;
double tw = useBoost ? totalWeight_cached : totalWeight_base;
const auto& cw = useBoost ? cumWeights_cached : cumWeights_base;
double u = R::unif_rand() * tw;
int moveIdx = 0;
while (moveIdx < nMoves - 1 && u > cw[moveIdx]) ++moveIdx;
```

The `!data->qHeterogeneity` guard ensures we don't boost partial-CL moves
when Het is active (M-114: partial CL not supported for Het).

### Parameter threading

1. **C++ side**: Add `double cacheBonus = 1.0` parameter to
   `run_mcmc_batch_cpp`. Default 1.0 = no boost (backward compatible).
2. **R side**: Add `cacheBonus` field to `MkPrimeMCMC()` (default 5.0).
   Pass through `.RunMkPrimeSingleRun()` → `run_mcmc_batch_cpp`.
3. **Adaptation integration**: The tuning bandit already adjusts base weights
   by ESS/sec. Cache-aware scheduling stacks on top. No conflict: the bandit
   sees actual ESS/sec (which reflects the boosted selection frequency), and
   adjusts base weights accordingly.

### Diagnostics

Add two counters to the batch result for monitoring:
- `n_cache_hits`: iterations where cache bonus was active
- `n_cache_misses`: iterations where base weights were used

These let the R side compute % cache utilization per batch.

## Changes

### `src/mcmc.cpp`

In `run_mcmc_batch_cpp()`:
- Add `double cacheBonus = 1.0` parameter
- After building `cumWeights` (base), build `cumWeights_cached` with boosted
  weights for partial-CL-eligible moves
- In the per-chain loop, select weight array based on cache state
- Add diagnostic counters

### `R/MkPrimeMCMC.R`

- Add `cacheBonus = 5` parameter to `MkPrimeMCMC()`
- Document: multiplier for partial-CL move weights when node cache is valid

### `R/RunMkPrime.R`

- Pass `mcmc$cacheBonus` to `run_mcmc_batch_cpp` call site (~line 862)
- Accumulate `n_cache_hits`/`n_cache_misses` if desired for logging

### `src/RcppExports.cpp` / `R/RcppExports.R`

- Auto-generated by `Rcpp::compileAttributes()`

### Tests

- Unit test: verify that with `cacheBonus > 1`, partial-CL moves are
  selected more often when cache is valid (statistical test on
  propose_counts from a short batch)
- Regression: existing test suite should pass unchanged (default behavior
  when `cacheBonus = 1.0`)

## Risks

- **Low**: Mechanical change to weight selection. No change to any move's
  proposal or acceptance logic.
- **Tuning bandit interaction**: The bandit will see higher propose counts
  for partial-CL moves when cache is active. Since it optimizes ESS/sec
  (not ESS/proposal), this is correct — it will lower base weights for
  moves that are getting extra proposals via the bonus if they're not
  contributing proportionally to ESS.
