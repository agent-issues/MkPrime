Worth elevating to an explicit instruction: "if the brief names a file that doesn't exist, locate the actual implementation, cite both the wrong brief and the real path, and proceed."

- **Caveat-flagging convention works well for orchestration.** L4 produced two caveats (F81-Het exchangeability → L1; relabelling↔ascertainment commutation → L5) tagged for downstream lanes. This is exactly the pattern the orchestrator needs to weave waves together. Worth elevating in the math-prover profile: "when a step would require a separate proof, label it explicitly as a follow-up and indicate which lane / role should pick it up."

- **The <200-word return summary is the right cadence.** All five agents stayed within budget; orchestrator could update the campaign log from the return message alone, without reading the full proof. Keep.

- **Open-question status is more useful than forced-watertight.** L3's two OPEN findings (SWAP-001 / SWAP-002) with explicit empirical follow-ups (β=0 uniformity test) are exactly the right shape. The profile already says "do not handwave; open question is better than false watertight" — confirmed working as intended.

### From Wave 2

- **Worktree base lags the orchestrator's HEAD.** L6 reported its worktree base was `2bc4da7` (pre-Wave 1) while orchestrator main HEAD had advanced to `34a2607`. The agent worked around it correctly by using `git show 34a2607:dev/red-team/proofs/relabelling-correction.md`, but the Wave 2 dispatch prompt told agents Wave 1 artefacts would be "in `dev/red-team/proofs/` in your worktree". That instruction was wrong. Profile fix: tell agents to (a) check `git merge-base HEAD main`, (b) if main is ahead, read newer artefacts via `git show <main-hash>:path`. Also confirms `feedback_verify_agent_base` is still load-bearing — worktrees branch off the original main HEAD at *agent dispatch time*, not at *agent run time*.

- **Out-of-lane verdict is a useful escape valve.** L6 was asked to re-derive R5-4, but R5-4 turned out to be an empirical claim (post-relabel phi-median distribution dependent on a downstream scoring function), not a math claim. The agent didn't force-fit a proof — it declared R5-4 out-of-lane and explained why. Worth elevating in the math-prover profile: "if the brief asks you to prove something that is fundamentally empirical, say so and identify the right type of follow-up (heavy test / simulation rerun / etc.)."

- **Identifying latent-but-not-active bugs.** L6 surfaced LS-001 as a logseries-version of EG-001 that is currently *latent* because `kprimeLogseriesC` is fixed. The agent correctly noted the bias cancels in MH ratios at fixed `c` but is a hazard if `c` becomes sampled. This is exactly the kind of "the audit reaches further than the current code paths" finding that justifies math-prover work — confirming the profile's emphasis on first-principles derivation pays off.

- **Agent pushed back on the orchestrator's brief with primary evidence.** N2's brief instructed it to audit `log(1−p) → log1p(−p)` as a likely cancellation site. The agent ran the experiment (Experiment 6: zero difference at p = 1 − 10⁻ⁱ for i=1..16) and found the two formulations are *bit-equivalent in IEEE 754 doubles* across the reachable range — once `p` is stored as a double, `1.0 − p` rounds once and both formulations consume that rounded value. The real precision loss is upstream in computing `p_const`. The agent captured the 16-site patch but marked it cosmetic and did not recommend application. **This is exactly the behaviour the role spec wants** — "if you have primary-source evidence that contradicts a specific claim … adapt". The numerical-auditor profile's "quantify, don't qualify" instruction enabled this. Worth elevating in the profile: "if the brief hypothesises a numerical issue, verify it numerically before working on the fix — the brief may be wrong."

- **`fast_neg_exp` audit reframed the search.** N1's brief asked about the matrix-exponential primitive itself. The primitive turned out to be stable; the actual bug (FAST-EXP-001) was in the *algebra around* it — `(1/k) - (1/k)·exp(arg)` and F81's `1 − d` are cancellation-prone at small `rt`, regardless of whether `exp` is computed exactly. The agent followed the conditioning all the way through. The profile's instruction "conditioning analysis first, stress test second" paid off.

### From Wave 3

- **Quick-mode tests must be self-calibrating about their own statistical power.** D2 ran a chi² uniformity test on `GibbsSubtreeSwap` and `WeightedSubtreeSwap` at 5-tip × 2000 samples and got p=0.979 / p=0.749 — apparent PASS. The agent correctly refused to declare SWAP-001/SWAP-002 refuted: "at n=5 with 2000 samples, partner-set asymmetries may be too small to surface." This restraint is exactly what the role spec asks for ("do not silently widen tolerances to make a test pass"). Worth elevating in the mcmc-diagnostician profile: "if a quick-mode test is structurally underpowered to detect the bug it targets, say so explicitly; never report PASS without a power statement."

- **C++-side diagnostic counters can be the heavy test.** N3 found that `src/mcmc.cpp` already cross-checks every partial-CL move against full-eval (`diagMaxDiff`, per-move-type mismatch counters at `src/mcmc.cpp:4608-4727`). The N3 harness is essentially a thin reader of `pcl_diag.txt`. This made the harness ~0.4s in quick mode. Lesson: before designing a heavy test from scratch, check whether the production code already has the diagnostic plumbing and just isn't surfacing it. Worth adding to the mcmc-diagnostician and numerical-auditor profiles.

- **advisor() reconcile worked correctly on a design decision.** D1 called advisor() to reconcile whether topology rank could be included in SBC. Outcome: rank-uniformity is for continuous parameters; bucketing RF distance would smuggle in an arbitrary threshold; topology was correctly excluded. The role spec already mentions advisor() implicitly (via the inline instructions); the mcmc-diagnostician profile could make it explicit: "for design decisions that materially affect what your test is testing, advisor() before committing."

- **Multiple agents reported `R/RcppExports.R` / `src/RcppExports.cpp` regenerated** by `pkgload::load_all()` in their worktrees. These are auto-generated files; they appear modified in worktree status but the agent didn't touch them. The orchestrator's integration step must NOT stage these. Worth noting in the harness-side documentation: agents touching the package via `load_all()` will see these regenerated. Profile fix: explicitly tell agents to expect this and not flag it as a worktree-state concern.

   length × Dirichlet(1,…,1) on edges. **Worst-case mismatch**:
   inference mean ≈ `expSteps` ≈ 68 vs simulation mean ≈ 2.3 → ranks pile
   at 0 (posterior >> truth) in every arm. **Fix**: pin
   `EXPSTEPS_FIXED = 50`, draw `tree_length ~ Gamma(2, 2/50)`, edges via
   normalised iid Exp(1) (= Dirichlet(1,…,1)). Same `expSteps = 50` then
   passed to `MkPrimeModel()`, removing the `expSteps = tl_true × N_CHAR`
   leak that double-coupled inference prior to ground truth.
2. **ACRV mismatch**: forward `.simJCchar` uses a constant per-character
   rate (no Gamma-discretised rate variation); inference defaults
   `nCat = 6L` with `rate_log_sd ~ Gamma(1, 1)` actively integrated.
   **Fix**: pass `nCat = 1L` in `modelArgs`. L7 already proved ACRV
   analytically — SBC doesn't need to re-test that path.
3. **rate_log_sd truncation**: harness clamped sampled `rate_log_sd` at
   3.0 ("to keep simulation tractable"); inference has no truncation.
   **Fix**: removed the clamp.
