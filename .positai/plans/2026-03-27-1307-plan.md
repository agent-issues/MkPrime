# Plan: Parallel MCMC Runs via `future` (M-093)

**Date:** 2026-03-27  
**Goal:** Parallelize independent MCMC runs for scalability on both
workstations and HPC clusters, using the `future` package as the
backend-agnostic parallelism layer.

---

## Background and constraints

### What is currently sequential

The `for (run in seq_len(nRuns))` loop in `RunMkPrime()` (and its copy
in `ResumeMkPrime()`) iterates independent runs one after another in a
single R process. Within each run, the C++ `run_mcmc_batch_cpp()` call
runs all `nChains` chains sequentially. There is no CPU-level
parallelism anywhere.

### The XPtr problem

`mcmcData` and `chainStates` are Rcpp `XPtr<T>` objects — raw C++ heap
pointers. They cannot be serialized and sent to worker processes. Any
parallel strategy must reconstruct them from plain R objects inside each
worker. Crucially, `ResumeMkPrime()` already does exactly this when
resuming from a checkpoint: it takes serialized R lists and calls
`init_mcmc_state()` + `fill_partition_cache()` + `allocate_cl_workspace()`
to rebuild the C++ state. This is the template for what each parallel
worker must do.

### Why `future`

- Single API covering multisession (sockets), multicore (fork), and
  HPC schedulers (SLURM, PBS, LSF) via `future.batchtools`.
- CRAN-friendly: lives in `Suggests`; runs fall back gracefully to
  sequential if the package is absent.
- Industry standard in the R/Tidyverse ecosystem (used by `furrr`,
  `targets`, etc.).
- The user sets `future::plan()` *before* calling `RunMkPrime()`;
  the package never calls `plan()` itself (CRAN policy).

### Why persistent workers (not segment-based)

The alternative — submitting a new batch of `nRuns` futures every
`checkEvery` iterations — incurs XPtr-reconstruction overhead and, on
HPC, job-submission latency on every segment. Persistent workers avoid
both: each worker runs its entire chain, checking a cancel file every
200 iterations (M-081 infrastructure). The orchestrator signals
convergence by writing cancel files.

## Design

### New user-facing parameters (`MkPrimeMCMC()`)

| Parameter | Type | Default | Notes |
|-----------|------|---------|-------|
| `parallel` | logical | `FALSE` | `TRUE` enables `future`-based run parallelism when `nRuns > 1`. |
| `pollInterval` | integer | `10L` | Seconds between convergence polls (parallel mode only). |

`parallel = FALSE` is the default to respect CRAN's requirement that
packages not consume unexpected parallel resources.

### Architecture: orchestrator + persistent workers

```
RunMkPrime(parallel = TRUE):
  ├── Validate: future package installed; nRuns > 1
  ├── Ensure logFile is set (auto-assign tempfile() if NULL, with message)
  ├── Generate per-run cancel files (cancelFile_1, cancelFile_2, …)
  ├── Serialize initial state for each run (R lists, no XPtrs)
  │
  ├── Launch nRuns persistent futures:
  │     future_i = future::future(RunMkPrimeSingleRun(
  │       serialised_state_i, mkd, model, mcmc,
  │       logFile = logFilePaths[i], cancelFile = cancelFiles[i], …
  │     ))
  │
  └── Orchestrator polling loop (main process):
        repeat {
          Sys.sleep(pollInterval)
          samples ← ReadMkLog(logFilePaths)   # read from disk
          check convergence (ESS / PSRF)
          if (converged) → write all cancelFiles
          if (maxTime exceeded) → write all cancelFiles
          if (all futures resolved) → break
        }
        results ← lapply(future_list, future::value)
        .BuildResult(results, …)
```

Workers check for their cancel file every 200 iterations (existing
M-081 logic), save a checkpoint, and return cleanly.

### Streaming mode and log files

Parallel mode **requires** streaming (`logFile` set), because that is
the only way the orchestrator can read in-progress samples from running
workers. If the user does not supply `logFile`, `RunMkPrime()` silently
assigns one per run under `tempdir()` and emits a `cli_alert_info`
message explaining where they are.

### `RunMkPrimeSingleRun()` — the key internal function

This new internal function encapsulates everything a single run needs to
do, extracted from the existing per-run loop body in `RunMkPrime()`:

**Inputs** (all R-serializable, no XPtrs):
- `mkd` — `MkPrimeData` object
- `model` — `MkPrimeModel` object (finalized)
- `mcmc` — `MkPrimeMCMC` object
- `initialState` — named R list (same format as `.SaveCheckpoint()`
  serialization: `edge`, `rel_br_lengths`, `tree_length`, etc.)
- `moves` — list of move descriptors
- `tipLabels` — character vector
- `runIdx` — integer
- `logFile`, `cancelFile`, `checkpointFile` — paths

**Inside the worker:**
1. Reconstruct `mcmcData` XPtr via `.InitMcmcData(mkd, model)`
2. Reconstruct `chainStates` XPtrs via `init_mcmc_state()` +
   `fill_partition_cache()` + `allocate_cl_workspace()`
3. Run the batch loop (calling `run_mcmc_batch_cpp()` in 200-iteration
   batches) — same logic as the existing inner loop
4. Stream samples to `logFile`; check `cancelFile` each batch
5. Save checkpoint periodically if `checkpointFile` is set

**Returns** (R-serializable):
- Serialized final chain states (same format as checkpoint)
- Tree samples (as `multiPhylo`-style list)
- Accept/propose counts, tuning, swap rates
- `saved_idx`, `stop_reason`, `actual_iter`

### Code refactoring benefit

`RunMkPrime()` and `ResumeMkPrime()` currently contain ~400 lines of
near-duplicate batch loop code. Extracting `RunMkPrimeSingleRun()` fixes
this duplication: both functions initialize state and then delegate to
`RunMkPrimeSingleRun()`. This is a correctness win independent of
parallelism.

### M-093b — Parallel orchestration

**File:** `R/RunMkPrime.R`, `R/MkPrimeMCMC.R`, `DESCRIPTION`  
**Priority:** P2  
**Depends on:** M-093a

Steps:
1. **DESCRIPTION:** Add `future` to `Suggests`.
2. **`MkPrimeMCMC()`:** Add `parallel = FALSE` and `pollInterval = 10L`
   parameters; validate and store in the S3 object.
3. **`RunMkPrime()`:** At the top of the function, branch on
   `mcmc$parallel && mcmc$nRuns > 1L`:
   - **FALSE (sequential):** existing code path calls
     `.RunMkPrimeSingleRun()` in a `for` loop (M-093a result).
   - **TRUE (parallel):** call `.RunParallelRuns()`.
4. **`.RunParallelRuns()`** (new internal function):
   - Validate `future` is installed; abort with an install hint if not.
   - If `mcmc$logFile` is `NULL`, auto-assign `tempfile()` paths with
     `cli_alert_info()`.
   - Derive per-run cancel files from `MkCancelPath()` or temp paths.
   - Launch `nRuns` non-blocking futures via `future::future()`, each
     calling `.RunMkPrimeSingleRun()` with per-run paths.
   - Enter the polling loop:
     - `Sys.sleep(mcmc$pollInterval)`
     - Read log files via `ReadMkLog()`; call `.CheckConvergence()`
       using the streaming-from-disk path (same logic as
       `.ConvWindowRows()` but reading from the log matrix)
     - Update `cli` progress display (ESS / PSRF / elapsed)
     - Write cancel files if converged or `maxTime` exceeded
     - Break when `all(vapply(fList, future::resolved, logical(1L)))`
   - Collect `lapply(fList, future::value)` and return the results list.
5. **`.BuildResult()`:** Already accepts a list of per-run results;
   ensure it works from the parallel path's return format.

## What is NOT in scope

- **Within-run chain parallelism** (parallelizing the `nChains`
  temperature ladder within a single run). The chains must communicate
  for swap proposals, which requires shared C++ memory. This would need
  OpenMP or a different swap mechanism and is a separate, more complex
  effort.
- **C++-level threading** (OpenMP, TBB). Out of scope for this task;
  would require changes to the C++ hot loop.
- **`parallel::makeCluster()` fallback.** A single dependency (`future`
  in Suggests) is simpler and more capable than maintaining two parallel
  backends.
- **Auto-detecting the number of runs from `future` workers.** The user
  sets `nRuns` explicitly; `future::plan()` determines how they are
  scheduled.

## HPC usage notes (for documentation)

On a SLURM cluster, each `future` worker becomes a separate job
submission. Key recommendations to document:

- Use a large `checkEvery` (e.g. `50000`) to reduce the frequency of
  log-file reads in the polling loop; SLURM jobs have startup overhead
  but are fast once running.
- Set `logFile` explicitly (don't rely on tempdir, which won't be shared
  across compute nodes unless on a shared filesystem).
- Set `checkpointFile` so runs can be resumed if the master job
  times out.
- `pollInterval` of 30–60 seconds is more appropriate for HPC than the
  default of 10.
